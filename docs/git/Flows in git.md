# Flows работы с гитом

## Проблематика

Незнакомая с практиками совместной работы группа разработчиков скорее всего начнет сталкиваться с проблемами взаимодействия например, несогласованных изменений "ломающих" основную ветку разработки или множество веток в которых не возможно найти рабочую.
Любой Flow работы с Git это набор простых практики подходящих для любых небольших команд, занимающихся разработкой продуктов. Для больших команд или нескольких команд, работающих в одном репозитории практики добавляются, не меняя корневые идеи.
Flow работы стратегически отвечает на два вопроса: 
- **Как осуществляется координация работы с кодом нескольких разработчиков?**
- **Как код готовится к выкладке в среду или релизу**

## Работа с кодом для нескольких разработчиков

Почти всегда Flow работы над задачей универсален и различается деталями: названием создаваемых веток, порядком ревью, требованием к коду для создания ревью.
Общий порядок:
 - Создать новую ветку. Часто имя так или иначе привязывает ветку к задаче над которой ведется работа в рамках [[Workflow]].
 - Разработчик ведет работу над веткой
 - Проводится ревью работы другими разработчиками
 - Новый код тестируется командой тестирования
 - После прохождения ревью и тестирования код сливается. Это может быть сам разработчик или ответственный за слияние

Ревью может быть и формальным, когда разработчики совместно смотрят коммит, так и высоко формализованным, когда ревью требует формального одобрения команды тестирования/автотестирования и верификации когда участниками смежных команд.

С точки зрения рабочего процесса, Одна задача - одна ветка - один PullRequest. Т.е. лучше не группировать реализацию нескольких задач в одной ветке.  
НО  
Если при разработке выяснилось что задача разбивается на несколько логических блоков, то каждый можно и нужно делать отдельно.  
Если одна доработка исправляет несколько проблем, то каждую можно упомянуть.
Если хочется проверить промежуточные результаты можно сделать Коммит или PR и попросить посмотреть его.  
Если состояние совсем промежуточное. то из ветки разработки можно выделить ещё одну новую под ветку и сделать PR на слияние под ветки в ветку разработки.

## GitFlow vs GitHubFlow vs GitLabFlow

Различие между наиболее Flow работы с Git появляется в основном не из-за требований работы команды с кодом, а в первую очередь из-за процессов доставки готового года до потребителя: создания инсталляторов для desktop приложений, публикации релизов в облако или магазин приложений.
Самый простой вариант используется, когда публикация не требует особой подготовки, выкладка происходит одного места налаженным процессом. Это вариант GithubFlow или TrunkFlow который предполагает одну рабочую ветку в которую происходит слияние изменений и из неё-же происходит публикация релизов.
В случае, когда подготовка к релизу длительная, включает несколько этапов или работы смежных команд имеет смысл использовать GitFlow. Он подразумевает создание релизных веток для подготовки релизов и ветки master куда сливаются уже готовые релизы.
GitLab Flow это не единый Flow, а семейство. В нём может присутствовать разные релизные ветки для случаев, когда, например, есть выпуск сборок для внешних клиентов. Ветки для разных сред (DEV, EU, US, JP) или для разных этапов подготовки (DEV, PreProduction, Production).
Flow может и должен меняется со временем. С переходом на новые жизненные циклы продукта, с его развитием Flow будет подстраиваться под потребности команды, бизнеса и пользователей. Любая схема и изменения должны проходить через призму текущих потребностей, а не абстрактной статьи из интернета.
